# 2026-08-22 — SignalWire messaging: first delivered text, and what it cost

The shared number went from *one failed message ever* (Twilio, error 30034,
2026-07-21) to delivering texts end to end. Seven commits shipped; three of the
bugs were only findable by actually running the rail.

## What actually blocked the number, in order

Six separate things, each invisible until the one before it was cleared. Three
of them fail **silently** — no error anywhere.

1. **A dead assignment record occupied the number.** Re-assigning returned
   `422 invalid_list_items` — *"Not available to assign within the project"* —
   until the FAILED assignment was `DELETE`d. "Just retry it" could never have
   worked, and the error message points at capability, not occupancy.
2. **No `status_callback_url` had ever been registered**, so the carrier's reason
   was never delivered anywhere. Re-created the order with one; the assignment
   reached `completed` in ~12 minutes.
3. **Inbound pointed at a dead staging Supabase project** and used
   `swml_webhooks`. Repointing needs handler *and* URL together — and SignalWire
   creates a **new** `cxml_webhook` Fabric resource rather than repointing the
   old `swml_webhook`, which is left orphaned (`6db2d8f3`, still pointing at
   staging).
4. **`sms_sender_numbers` was empty**, so every send returned `blocked_sender`.
   Its LIVE activation CHECK is far stricter than the first copy of the table in
   `schema.sql` — that file contains **more than one definition**; read
   `pg_constraint`, not the file.
5. **`accounts.high_value_lead_amount` was null**, and `Number(null) || 0` is 0,
   so `highValueThreshold > 0` made every lead non-high-value. No alert could
   ever fire. The field lives in a **nested** disclosure (Automations → Smart
   Intake → "Advanced"); setting it while collapsed silently does nothing.
6. **The service-area gate prunes `out_of_area`** and the served-city list is
   still the template default (Maplewood, Springfield, Oakdale…). A submission
   from a real nearby town is pruned to `low` and sends nothing.

   **Corrected 2026-08-22, later the same day.** "Pruned" was the wrong word and
   would mislead anyone reading this back. The lead is never removed — it lands
   on the board like any other. What it loses is the ALERT: a prune flag makes
   high-value impossible by construction, forces the score to `low`, and the
   low-quality mute then suppresses the owner alert. Full mechanism and the
   product decision it needs are in
   [Two-Way Messaging Readiness](../docs/two-way-messaging-readiness.md), E1.

## Proven, not assumed

- Outbound **delivered** (not merely accepted) twice: 11s and 22s end to end.
  `provider_accepted_at` and `delivered_at` are separate columns; a row that
  stops at accepted is the 30034 shape wearing a success costume.
- Inbound works — first ever. `STOP` flips the ledger **and** genuinely
  suppressed a qualifying high-value alert; `START` restored it.
- Callbacks delivered, stored, and **signature-verified 2/2**.

## The callback signature scheme (undocumented by SignalWire)

Solved offline against two captured `(body, signature)` pairs:

```
HMAC-SHA1(SIGNALWIRE_SIGNING_KEY, callback_url + raw_body) -> HEX
```

**Hex**, not the base64 the rest of the rail uses via `signBase64` — reusing
`validateWebhookSignature` here would reject every genuine delivery. The signed
URL includes the secret path segment, which is what makes verification possible
**without** migrating to a static path. Shipped measuring, not enforcing:
`LGQ_SIGNALWIRE_REGISTRY_REQUIRE_SIGNATURE=1` turns on rejection once real
traffic reads `valid` consistently.

## Mistakes worth keeping

- **Rotating the callback token is a carrier operation, not a config change.**
  The URL embeds the token, so rotation forces delete + re-create of the
  assignment. Doing it on a `completed` assignment broke it: the replacement
  failed **one second** after creation (vs ~12 minutes to succeed), and **no
  callback fired for that failure**. Only rotate when a failed assignment costs
  nothing.
- **The token leaked twice, identically.** A watcher captures the token at
  startup to build its redactor; rotate while it runs and it prints the new one
  verbatim. The fix is ordering — kill every watcher before rotating.
- **`sms_sender_numbers` can outlive the truth.** After the failed rotation the
  row still said `active`/`assigned` while SignalWire said `failed`, which would
  have sent on an unattached number. `scratchpad/sync-sender-truth.mjs` reads
  the provider and writes what is true.
- **A green pipeline and a broken feature coexist comfortably.** Every gate was
  green before the first text; the dead dashboard link and the inbox conflation
  were both only visible once a real message landed.

## The inbox called everyone by their phone number

Raised off a screenshot: a thread headed `810-304-2061` on the left, with
**BRETT** and a "View full profile" button on the right — the same
conversation, labelled two different ways on one screen.

Two faults, stacked:

1. **The list read the wrong tables.** `buildContactNameMap` read `jobs` and
   `leads`. The pane beside it (`messageContext`) reads **`clients`**. A
   customer who exists only in the address book therefore had a name in one
   half of the screen and not the other. Confirmed against production: for
   account `c63293b4`, `+18103042061` resolves to `BRETT` from `clients` and
   from nothing else.
2. **There was no rung between "has a name" and "is a number."** Most rows
   carry an address even when nobody typed a name.

The label now falls through in the order an owner would ask: **name, then
street, then town, then the number.** `streetFromAddress` sits beside the
existing `cityFromAddress` and works *forwards* — the street is the first
segment that looks like one, so a business name or an `Apt 4B` line in front
of it is skipped rather than printed. `cityFromAddress` works backwards from
the state/ZIP tail. A test asserts the two never claim the SAME segment,
because if they did the city rung would be dead and nobody would notice.

**`name` and `label` are separate fields, and must stay separate.**
`starterRepliesFor()` greets by first name. Writing the street into `name` to
save a field would open every saved reply with "Hi 1418". `name` stays a real
name or null; `label` is display-only and never null. The page keeps both, and
a test asserts `starterRepliesFor(activeName)` and not `activeLabel`.

Two smaller consequences, each of which would have been a bug on its own:

- The number is a subtitle whenever the heading is something else. That rule
  used to key off `activeName`; keyed off the name, a street-headed thread
  would have lost its phone number from the screen entirely. It now keys off
  whether the label differs from the number.
- Search matches the label too. Typing the street you can see on the row had
  to find it; matching only the name meant it did not.

Identity merging is **field by field**, not row by row: a job carrying a
service address but no usable name must not blank out the name a lead
supplied. Precedence runs leads → jobs → clients, weakest first, so the list
agrees with the pane rather than merely being less wrong than before.

Verified by mutation, not by reading: dropping the `clients` read fails 4
tests, and collapsing the fallback chain fails 3.

**On this account it changes exactly one row.** The other five threads have no
client, job or lead in this workspace at all, and stay as numbers — which is
honest. No row in this account has an address yet, so the street and town
rungs are proven by test rather than on screen.
## One missing grant, and why nothing shouted

`/admin/messaging` has said *"inbound SMS action queue could not be read"*
since the queue shipped. `loadMessagingOperationsHealth` reads three task
tables with the service-role client:

| Table | service_role |
|---|---|
| `sms_delivery_tasks` | `SELECT` |
| `payment_sms_producer_tasks` | `SELECT` |
| `sms_inbound_action_tasks` | **nothing** → `42501` |

`20260821192000` revokes ALL on that table from every role and then grants
EXECUTE function by function — stricter than either sibling, and deliberate.
The observability code was written against direct table reads anyway, so the
page went half-blind on the day the queue shipped.

**The rail itself was never affected**, which is why nothing else complained.
The worker claims, applies, completes and fails through SECURITY DEFINER
functions, every one already granted EXECUTE to `service_role`.
`enqueue_sms_inbound_action_task` has no grant at all and is *correct*: it is a
TRIGGER function, and EXECUTE on those is checked at CREATE TRIGGER time, not
when the trigger fires. Reading a missing grant there as a second defect would
have been wrong.

Fixed with `SELECT` only, for `service_role` only — the role already holds
BYPASSRLS, so it grants no visibility that role could not already obtain
through the RPCs it can execute. Writes stay RPC-only; `anon` and
`authenticated` stay at nothing. All four asserted in the migration and again
in the verifier.

**The check that existed could not have caught this.** The PG17 verifier
asserted `!auth_select` and `!service_update` and never named `service_select`
in either direction — so the one privilege that was wrong was the one nothing
looked at. It is now asserted both ways: readable, and still not writable.
Confirmed by mutation — skipping the new migration takes the harness to 29/30
and exit 1.

The harness itself had never run here: `npm run test:pg17:sms-inbound-actions`
exits **2** with an install command when `embedded-postgres` is absent, and
exit 2 is not a pass. Installed pinned to 17.x with `--no-save`, hydrated by
hand past npm's allow-scripts block, and the contract then ran **30/30**
against a real engine.

What the dashboard had been hiding, now that it can see: one task, `completed`,
one attempt, outcome `{"decision":"unclear","action_kind":"none"}` — the test
message, handled correctly. Nothing was wrong behind the banner. That is the
good outcome, and it was unknowable while the read failed.
**Swept for the same shape elsewhere, and it is clean.** Eight other tables in
`public` are unreadable by `service_role`:
`billing_direct_checkout_late_success_{resolutions,tasks}`,
`billing_direct_payment_settlement_{attempts,tasks}`,
`legacy_destination_checkout_{event_receipts,operations,session_adoptions}` and
`stripe_merchant_provisioning_operations`. Every one has **zero** mentions
anywhere in `src/` — not just zero `.from()` calls — so all eight are
genuinely function-only and the grant matches the code. This table was the only
one where the two disagreed.
