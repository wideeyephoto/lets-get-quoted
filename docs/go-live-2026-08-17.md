### What this proves that nothing had proven before

**Applying `20260816221500` did not break the ungated legacy rail.** That foundation
adds `protect_legacy_destination_checkout_payment_lineage`, a trigger on the live
`payments` table, and until this capture nobody had run a real payment through the
legacy path with it installed. It permits the old mutable Session pointer while both
new lineage pointers are null — which is exactly the state the legacy rail writes —
and the transaction confirms it. `current_legacy_destination_checkout_operation_pk`
and `legacy_destination_checkout_paid_hold_operation_pk` are null on all 268 rows, so
the generation gate really is off and the new ledger really is untouched.

Both legacy destination variants had also never been run end to end against a real
capture. Settlement and refund now have been.

### Two defects the smoke test caught, one of them mine

Step 2 was not ceremony. Both fixes below landed between the credential swap and the
verified capture, and neither would have been found by the test suite.

**`d972c39d` "Disambiguate legacy payment reads"** — this one is a consequence of the
migration sequence. `getPublicPayment` and `sendPaymentSmsEvent` embed related rows via
PostgREST (`job:jobs(...)`, `account:accounts(...)`). Several tables installed on
2026-08-17 carry foreign keys to **both** `payments` and `accounts`/`jobs`, which
PostgREST reads as a second join path and therefore an ambiguous embed. The fix pins
the relationship explicitly — `jobs!payments_job_id_fkey`,
`accounts!payments_account_id_fkey` — with a new regression test at
`test/payment-postgrest-relationship-hints.test.ts`.

The lesson is worth keeping, because the analysis that cleared these migrations missed
it: **a migration can be structurally dark and still break the application.** Every
check applied beforehand asked what the SQL *creates, mutates or gates*. None asked
what it does to PostgREST's inferred relationship graph, and that graph is derived from
foreign keys the migrations legitimately added. `/pay` is the read path for the payment
page — the break was in front of every customer, and only a real request surfaced it.

**`c96be537` "Propagate payment metadata to Stripe charges"** — metadata was set on the
Checkout Session only. PaymentIntent metadata snapshots onto the Charge, and
`charge.refunded` needs `payment_id` to route a **Dashboard-issued** refund back to the
right row. Without it, exactly the refund performed in Step 2 arrives unattributable.
Found by doing the refund rather than by reasoning about it.

### The pointer count is 1 now, and that is correct

The "must be 0" check earlier in this document is an **install-time precondition, not a
steady-state invariant**. The legacy rail writes `stripe_checkout_session` whenever it
creates a Session, so `6e2e7689…` carries one and the count reads 1.

The consequence worth knowing: **`20260816221500` can no longer be re-applied without
re-running a pointer cleanup.** Its preflight refuses at any non-zero count. That does
not matter for this database — the migration is applied and does not re-run — but a
fresh-environment replay of the sequence now needs the cleanup step again.

### Three columns are null on purpose — do not "fix" them

`stripe_charge_id`, `stripe_account_id` and `stripe_livemode` are all null on the live
audit payment, and on all 268 rows. That reads like a persistence gap. It is not: **all
three belong to the `direct` rail, which is gated off.** The legacy `destination` rail
predates them and was never meant to write them.

The evidence is in the code that consumes them. `direct-checkout-operation.ts:252-253`
*validates* rather than populates:

```
|| payment.stripe_account_id !== input.merchantAccountId
|| payment.stripe_livemode !== input.livemode
```

and `direct-refund-operation.ts:186` requires `stripe_charge_id` via `requireString`.
They are set in a single transaction by the direct-payment preparation RPC, not at settlement.

**And `stripe_livemode` being null is load-bearing, not incidental.**
`protect_payment_stripe_livemode` (`20260816073000:177`) makes the column immutable —
any `old is distinct from new` raises `22000 'payments.stripe_livemode is immutable'` —
with exactly one exception, `v_atomic_direct_preparation`, which requires:

```
old.charge_model = 'destination' and new.charge_model = 'direct'
and old.stripe_livemode is null and new.stripe_livemode is not null
and current_user not in ('anon','authenticated','service_role')
and current_setting('lgq.direct_payment_preparation_id') = old.id::text
```

So a destination payment can only convert to the direct rail **while its
`stripe_livemode` is still null.** Populating it at INSERT — which the trigger would
permit for a backend role — would make every such row permanently unconvertible, with
the conversion failing as `22000` rather than as anything legible.

Two further consequences of that immutability:

- The 268 existing rows can **never** be given a livemode. `null is distinct from true`,
  so a backfill `UPDATE` raises `22000`. That guard is working; do not route around it.
- Do not use `stripe_livemode` to separate live from test data — it will be null for
  every legacy destination payment forever. Use `test_marker`: live payments are
  unmarked, demo ones carry `backfill-test-markers:demo job or seeded client`.

The admin UI reads all three for display (`/admin/payments/[id]` shows Stripe mode,
Merchant account, Charge). They render as `—` for destination payments, which is
correct, and will populate once the direct rail is enabled.

## What "live" actually is here

**It is a credential swap, not a gate rollout.** The `/pay` destination-charge rail is
not gated — it is the legacy path that produced all 267 payment rows, and it runs
today against a test key. Changing `STRIPE_SECRET_KEY` to a live key is what makes
payments real. The 17 feature gates are all *dark new code*; none of them is required
for live payments, and turning them on is a separate, later, incremental rollout.

So: **Steps 1–2 below are "going live". Steps 3–4 are optional and can wait.**

## Not a blocker: the platform has no real users

Confirmed by the owner on 2026-08-17: **everything on the platform is demo. No real
payments, no real users, no real contractors.** The database agrees — 264 of 267
payments carry the demo `test_marker`, no unmarked row reads `paid`, no payment carries
a charge id, and all three billing tables are empty.

That removes the thing this section was originally written to prevent. The concern
below is real mechanically, but its consequence — a working contractor suddenly unable
to receive money — cannot happen, because there is no such contractor. **Go live
without waiting on it.** What follows is recorded so it is understood rather than
rediscovered.

## Step 2 — verify the rail is live, with the smallest possible real transaction

1. Confirm the deploy is serving and Stripe live-mode API logs now show traffic.
2. Create one real payment on `/pay` against `acct_1TuEg3GjJLVfg2pQ` — the one account
   proven live — for the smallest amount the flow allows. Pay it with a real card.
3. Confirm: the payment row reaches `paid`, `stripe_payment_intent` is bound,
   `paid_at` is set, `platform_fee` is populated in **dollars**, and the webhook
   delivery shows 200 in the Dashboard.
4. Refund it from the Stripe Dashboard and confirm `charge.refunded` lands and the row

That exercises settlement and the refund path end to end. Both legacy destination
variants have never been run end to end against real captures, which is the standing
gap this closes.

If Step 2 fails, Step 1 is reversible: put the test credentials back and redeploy.
Nothing in the database needs undoing, because a failed live attempt writes the same
rows a failed test attempt would.

## Step 4 — gates, one at a time, later

All 17 stay at 0 until someone deliberately turns one on, watches it, and moves to the
next. Two ordering rules carry over and do not expire:

- `LGQ_LEGACY_DESTINATION_CHECKOUT_GENERATION_ENABLED` goes on strictly **before**
  the projection gate, with a drain period.
- **`LGQ_LEGACY_DESTINATION_CHECKOUT_PROJECTION_ENABLED` must not be enabled at all
  yet, in any order, with any drain length.** `classifyLegacyDestinationCheckoutSignedEvent`
  has no production caller — grep returns its definition and its unit test only —
  while the gate unconditionally stands down the route's three write sites. Today it
  is a kill switch, not a switch: every destination payment would stop being settled
  or failed locally, with no write, no SMS, no job-feed event, no invoice
  reconciliation, no throw, no log, and a 200 back to Stripe. It becomes safe only
  once the webhook wiring slice lands and the classifier is actually called.

## What going live does not disturb

- All three billing tables are empty: `billing_events`, `billing_payment_operations`,
  `legacy_destination_checkout_operations`. Nothing to migrate or reconcile.
- 264 of 267 payments are demo-marked. The only unmarked rows are two `requested` and
  one `failed`. **No unmarked row reads `paid`** — there is no real money anywhere in
  the table, which is why the blast radius here is small.
- The demo rows will 404 against live Stripe if any reconciliation worker ever reads
  them by `stripe_payment_intent`. Only two carry one. Those workers are gated off; if
  one is ever enabled, filter on `test_marker` first.

## The one thing worth doing before real users, not before go-live

267 demo payments, 194 of them reading `paid` with `paid_at` timestamps and populated
`platform_fee`, will sit in production looking like settled revenue against Stripe
objects that do not exist. That is harmless while nobody is looking at reports, and it
is genuinely misleading the moment anyone is.

`scripts/remove-demo-data.mjs` exists for this. It is **not** a go-live step — going
live does not make the demo rows worse, and clearing them is destructive and should be
a deliberate, separately-reviewed pass. But it should happen before the first real
contractor onboards, so trailing-volume and fee-bracket maths are not computed over
$2,600 of money nobody ever collected.

The three unmarked rows (`4b86f692` requested, `bf0df2cb` failed, `ba1dcc4d` requested)
are the only ones that would survive a `test_marker` filter, and none of them is
`paid`, so the correct post-cleanup state is a payments table with no settled history
at all.
