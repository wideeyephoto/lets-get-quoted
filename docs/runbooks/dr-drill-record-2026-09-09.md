## Application defect corrected on staging

`crew_set_job_status(uuid, text)` writes `jobs.completed_at` when completing a job, but that column does not exist. The restored function hash matches the capture. A read-only production query confirmed the same missing column and function reference. The definition is in [the security-advisor migration](../../migrations/20260901000000_supabase_security_advisor_remediations.sql).

The original restore correctly reproduced this source defect. The follow-up [forward migration](../../migrations/20260909121506_fix_crew_job_completion.sql) removes that write, preserves the original `started_at`, casts text input to `job_status` and the returned enum to text, rejects a null status, and revokes anonymous execution. Assignment and archived-job guards remain. `schema.sql` now carries the same behavior. Production is unchanged and still requires this migration.

The first staging candidate exposed the enum/text mismatch (31/35 passed). After adding the casts, all 35 real RLS tests pass, including repeated completion, completion without a recorded start, archived-job refusal, cross-account refusal, and anonymous execution denial. The timestamp regression test uses an earlier stored value because PostgreSQL `now()` is constant within the fixture transaction. The HTTP RPC also rejects the anonymous role with 401 / `42501`.

The final function body matches the local migration. Supabase recorded the two candidate applications as `20260909121853` and `20260909122030`; the final local migration was generated by CLI before those applications. The [final verification](evidence/dr-completion-verification-2026-09-09.json) records both attempts and their results. The [advisor comparison](evidence/dr-completion-advisors-2026-09-09.json) shows the related anonymous-execution warning removed and no new findings. Other existing notices remain; see [Supabase's execution-grant guidance](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).

Baseline row parity was recorded before app use. The current database additionally contains sign-in/session state, login/tour/rate-limit activity, one `lead.status_changed` integration event at 11:02:05Z, and two migration-history rows. These changes are listed in the final evidence. Business-table counts remain at the captured baseline; the current database is not represented as byte-identical after use.

The test harness itself needed savepoints around expected SQL errors, updated assertions for deployed guard messages, and a closed-shift probe that changes the timestamp: `now()` stays constant throughout a transaction. Authorization assertions remain intact. Fixture rows roll back; PostgreSQL sequences may advance.

## Execution and remediation

The initial clock ran from **10:34:48.904Z to 11:12:21.584Z: 37 minutes 32.680 seconds**, ending with the crew-completion failure. Follow-up verification passed at **12:24:52.361Z**: **1 hour 50 minutes 3.457 seconds** after the first restore command, including the pause before the follow-up and corrective work. Neither number is a full-disaster RTO. Credential discovery, client installation and capture preceded the initial clock; infrastructure/provider recovery was not rehearsed.

1. Raw `pg_restore --clean` rolled back in 2.208 seconds because Supabase owns `pgrst_drop_watch`.
2. Disabled staging's `signalwire-sms-worker` cron job and confirmed no running jobs or queued HTTP requests before loading production data. It remains disabled.
3. Verified compatible Auth/Storage inventories, function/grant hashes, columns, constraints and managed migration histories. Preserved platform DDL, managed migration records, empty protected vector tables, staging's Vault secret and its extra cron/HTTP extensions. Production Vault was empty.
4. Used `restore-dr-managed.mjs` to rebuild application objects and load managed data in foreign-key order. Its first attempt rolled back because an identity sequence was dropped before its table. Corrected the ordering.
5. The managed restore committed in **334.174 seconds**. Supabase event triggers were retained and the application's `ensure_rls` trigger restored.
6. Comparison exposed excessive permissions inherited from staging's default grants. Quarantined API grants, reset object grants to PostgreSQL's baseline and replayed **661 archive ACL entries** in 88.605 seconds. All captured table/function grants then matched. The restore script now clears destination schema defaults before creating objects; a rolled-back database probe verified this for tables, functions and identity sequences.
7. Restored Storage through its API and checked signed-download hashes. API timestamps/version metadata change during upload; paths, lengths and bytes are the recovery contract.
8. Ran the relational validator, real RLS suite, existing-member callback and tenant denial, Storage reconciliation, app photo/PDF checks and page smoke. Retained the failing source-defect test.
9. Applied and verified the crew-completion corrective migration on staging. All 35 RLS tests passed; no fixture users/accounts remain. Checked Auth fields against the encrypted capture and denied a cross-account private Storage read with an actual authenticated client. Staging has zero active cron jobs and zero queued HTTP requests.

Database restores use one transaction and stop on errors. Temporary plaintext restore archives and SQL were removed afterward. Credentials pass through process environments, not command arguments. Restore tools reject production aliases, URL overrides, equal source/target and an unexpected project, and require an exact destruction acknowledgement.
