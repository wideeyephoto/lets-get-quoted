## Stripe gap procedure

**Stripe wins for actual external money state.** Database consent, actor/workspace ownership and audit records still determine whether an app action was authorized. Provider truth does not justify inventing a missing consent or initiating a new charge.

1. Obtain read access to live platform events, subscriptions, invoices, payment intents/charges, refunds, transfers, payouts and the relevant connected accounts. Confirm the account ID and `livemode`; a platform-only event list does not cover every connected account. The available restricted live key returned **403 `more_permissions_required`**, requiring `event_read`, so this drill did not complete event pagination or financial reconciliation. [Provider evidence](evidence/dr-provider-gap-2026-09-09.json).
2. Fully paginate events from T through C with a documented overlap at the snapshot boundary. Fetch current provider objects for all known subscriptions, payment intents, refunds and incomplete operations, including objects created earlier that changed after T. Treat event payloads as history and current objects as present external status. Stripe's event-list recovery window is limited; use current object inventories and provider reporting if T is older than the available events. [Stripe undelivered-event recovery](https://docs.stripe.com/webhooks/process-undelivered-events).
3. Compare by `(provider account, livemode, provider object/event ID)` against the restored inbox and immutable operation/ledger references. Stage a review report for missing receipts, terminal-state changes, amount/currency differences, credits already granted, and orphan provider objects. `scripts/reconcile-stripe-live-ledger.mjs` is a starting diagnostic; its bounded sample is not complete gap reconciliation.
4. Apply reviewed projection/inbox corrections through their supported idempotent paths. Replay only database projections whose external effects have been independently checked. Never replay a charge, refund, transfer, ad-wallet refill or credit issuance solely from a restored “pending” row. Stripe may prune idempotency keys after at least 24 hours, so an old key is not a permanent duplicate-effects barrier. [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests).
5. Re-read provider objects and all affected app ledgers after repair. Require zero unexplained amount/count differences and zero duplicate external effects. Drain the queued post-C events, reconcile a second cutoff, and then enable one worker at a time. Retain provider request IDs and repair audit evidence without secret values or customer data in public docs.
