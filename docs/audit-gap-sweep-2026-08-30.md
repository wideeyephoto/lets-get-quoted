## The audits to run, in order

### Before the first unknown customer

1. **Database backup + timed restore drill.** The worst finding of the sweep: **no database
   backup arrangement exists anywhere** — no pg_dump, no PITR record, not even the Supabase
   tier written down, so whether platform-side daily backups exist is unknown. Customer
   payments and invoices data has no backup the team controls, and customer file uploads
   (job photos, insurance docs, attachments) are in **no** backup of any kind. The repo/code
   rail is genuinely good (hourly USB, offsite bundles, verified 2026-08-30 08:02) — but no
   restore of any kind has ever been rehearsed. Run: pg_dump production → restore onto a
   scratch Supabase project → point a preview at it → log in. Time it. Record the tier.

2. **Failure-alerting drill (time-to-human).** Zero push-based alerting of any kind exists:
   no error-tracking SDK, no `error.tsx`/`global-error.tsx`/`instrumentation.ts`, no alert
   email, nothing. Every failure sink (webhook_failures, billing dead-letters, SMS DLQs,
   cron_runs) has only pull-based readers a human must remember to visit, and
   `inspect:cron-health` is invoked by nothing but a hand. Drill: manufacture a dead-letter
   in test mode and measure how long until a surface a human actually visits shows it.
   Cheapest immediate fix: a scheduled GitHub Actions run of `inspect:cron-health` that
   exits nonzero (CI email becomes the pager), then an ops-alert cron pushing Command
   Center troubles to the inbox that already works.

3. **Live-mode Stripe money rehearsal.** The plan-change rail landed and is proven — in
   sandbox only. No live-mode plan change has ever executed; the first real dollar, refund,
   and dispute path will run code no one has watched. Via the Codex operator (API, never the
   dashboard UI): dump live webhook endpoint config + enabled events + warning-email
   recipient, verify all live Prices, then run one real cheap purchase → refund end to end.

4. **Email deliverability run.** Never examined: DMARC is `p=none`, the root domain has **no
   SPF record**, and no inbox-placement test has ever been run. Also unverifiable from the
   repo: whether the production Resend webhook (the entire bounce/complaint auto-suppression
   chain) is registered at all — check `email_events` row counts in prod. Run: one of each
   email class (magic link, invoice+PDF, quote, campaign) to real Gmail/Outlook/Yahoo
   inboxes, plus a mail-tester score; then SPF + DMARC hardening at the registrar.

5. **Dependency patch pass.** First-ever `npm audit`: **2 critical + 8 high** in the current
   tree. `next` 14.2.15 is 20 patches behind its own line (two HIGH Server-Component DoS
   fixes land in 14.2.34/.35), Next 14 is out of security support entirely (a CSP-nonce XSS
   advisory will never be patched on 14.x), and the CI "Security audit" step added 2026-08-29
   has `continue-on-error: true` — it is red on every push and ignored. Bump to 14.2.35, run
   the full gate, make the CI step real, add Dependabot.

6. **Abuse-surface standing test.** The rate-limit helper is well designed (fail-open vs
   fail-closed variants exist) but coverage is Swiss cheese: AI endpoints that burn OpenAI
   tokens sit behind the fail-OPEN limiter with no global cap; **phone OTP is sent by the
   browser straight to Supabase** (`signInWithOtp` client-side), bypassing every app limit —

   invoice-pay creates Stripe Checkout Sessions unlimited. Add the standing vitest that
   walks every `api/**/route.ts` and public action and requires an explicit allowlist entry.

7. **Suspension-lifecycle test, after the in-flight RLS work lands.** Suspension currently
